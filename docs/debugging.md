# 🔍 Отладка агентов: «агент делает ерунду — что проверить»

[← назад к курсу](../README.md)

**Золотое правило:** прежде чем менять промпт, посмотри **траекторию** — что модель *на самом деле* видела и что вызывала. В нашем харнесе это `result.tool_log`, `result.messages` и `ScriptedLLM.calls`. 80% «модель тупит» — это «харнес прислал не то».

## Запросы к API падают

| Симптом | Причина | Что делать |
|---|---|---|
| `400` про tool_use / tool_call_id | на вызов инструмента нет результата, или результат без вызова | `repair_dangling_tool_calls`; проверь, что компакция не режет пару вызов → результат |
| `400` про чередование ролей | два user или два assistant подряд (у части провайдеров запрещено) | склеивай подряд идущие сообщения; после сводки вставляй «шов» |
| `401` / `403` | ключ, не тот провайдер или base_url | проверь `LLM_PROVIDER`, `LLM_BASE_URL`, что ключ от того сервиса |
| `404` модель | устаревший или опечатанный id | сверь id со страницей моделей провайдера |
| `429` | лимит запросов или токенов в минуту | backoff с джиттером, `retry-after`, меньше параллельности |
| `413` / контекст слишком длинный | история не помещается | компакция, обрезка результатов инструментов |
| Ответ обрывается посреди JSON | `max_tokens` слишком мал | увеличь; смотри `stop_reason` |

## Агент не вызывает инструмент

- Модель без поддержки tool use (особенно локальные) — проверь карточку модели.
- Описание инструмента не говорит, **когда** его вызывать. Добавь: «Используй для любых…».
- Инструментов слишком много или они похожи — модель путается. Объедини.
- В системном промпте противоречие («отвечай сразу» vs «сначала проверь»).

## Агент вызывает не то / с неправильными аргументами

- Имена параметров неочевидны (`q` вместо `query`). Переименуй, добавь описание и пример.
- Тип не указан или не тот. Харнес вернёт ошибку валидации — посмотри, исправляется ли модель со второго раза.
- Модель придумывает значения (id заказа, путь). Дай инструмент, который их перечисляет (`list_files`, `search_orders`).

## Агент зацикливается

- Ошибка инструмента неинформативна («error») — модель пробует то же самое. Пиши в ошибке, *что* не так и *что* попробовать.
- Инструмент возвращает одно и то же на разные запросы.
- Нет лимита шагов — поставь `max_steps`, логируй, когда он срабатывает.
- После отказа в разрешении модель повторяет вызов — текст отказа должен прямо говорить «не повторяй, предложи альтернативу».

## Агент «забывает»

- Сработала компакция и сводка потеряла факт — улучши промпт сводки, сохраняй ключевое в заметки/память.
- Факт был в результате инструмента, который ты обрезал.
- Долгая сессия без компакции — context rot: модель хуже находит важное в середине длинного контекста.

## Агент выдумывает

- Нет инструмента, который дал бы правильный ответ, — модель заполняет пробел. Дай инструмент или разреши говорить «не знаю».
- В промпте нет правила «числа — только из инструментов».
- Проверяй детерминированными eval'ами: «ответ содержит значение, которое вернул инструмент».

## Результаты нестабильны

- Это нормально: агенты недетерминированы. Меряй долю успехов за 5–10 прогонов.
- Уменьши свободу: меньше инструментов, чётче критерий «готово», явный план.
- Если нужна полная воспроизводимость — тесты на `ScriptedLLM`, а не на реальной модели.

## Дорого

- Посчитай: сколько шагов × размер контекста. Обычно виноваты длинные результаты инструментов и отсутствие компакции.
- Prompt caching для неизменного префикса (системный промпт + схемы инструментов).
- Дешёвая модель для субагентов и извлечения, сильная — только для главного решения.

## Чек-лист перед тем, как винить модель

- [ ] Я посмотрел полный запрос, который ушёл в модель
- [ ] Описание каждого инструмента говорит, когда его вызывать
- [ ] Ошибки инструментов объясняют, что исправить
- [ ] Есть лимит шагов и лог траектории
- [ ] Я прогнал задачу 5 раз, а не 1
